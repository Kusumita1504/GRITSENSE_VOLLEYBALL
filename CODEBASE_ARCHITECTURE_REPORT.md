# GRITSENSE Current Codebase Architecture Report

**Scope:** Source-level analysis of the current repository. Model-weight binaries (`.pt`, `.pth`, `.onnx`) were not opened. This is an architecture report, not an LLD.

## 1. Project Structure

- Root: `main.py` runs a YOLO player-tracking and video-overlay loop; `ball_tracker.py` is a separate ball-tracking helper; `plot_ball_trajectory` plots a CSV. `annotations.json`, `README.md`, and `requirements.txt` are root data/docs/dependency files.
- `Cappy_95_GNN_HRN/`: graph construction, GAT/HRN models, visualizers, graph/data loaders, and multiple alternative training workflows. `ball/` contains a standalone YOLO ball-video tracker and graph-data builder. `data/`, `graph/`, `models/`, `training/`, `visualization/`, and `tests/` contain the corresponding code.
- `epv_phase3/`: player video perception/logging, EPV state/action/outcome processing, MLP training/evaluation, examples and generated artifacts. `epv/` owns the EPV logic; `tests/` contains EPV tests.
- `GritSense_Temporal/`: independent temporal feature preparation, windowing, GRU/Transformer, trainer, tests, and synthetic examples.
- `Review 3/r3/`: separate integration snapshot with ONNX ball tracking, video overlays, local copies of graph/HRN/temporal modules, input data, and graph outputs.
- `__pycache__` directories are generated bytecode, not source. `Review 3/r3/output_graphs/` contains generated graph/visualization artifacts; binary files were not opened.

The repository is not one unified application: these areas have distinct entry points and only partial/internal connections.

## 2. Major Modules

### Root video tracking
**Files:** `main.py`, `ball_tracker.py`, `plot_ball_trajectory`

`main.py` reads a video, YOLO player weights, frame-indexed court corners, and a court image. It tracks players with Ultralytics `track`/BoT-SORT, maps player points using a homography, estimates speed, overlays court/player information, and writes `output.mp4`. It is a top-level script, not a function-based API.

`ball_tracker.py` defines `BallTracker` and `find_ball_by_color`. The class calls a supplied model to produce ball candidates, selects one using confidence and proximity to the prior position, estimates pixel-per-frame velocity, and draws a trail. Root `main.py` does not import/call it. The trajectory plotting script reads `ball_trajectory.csv` and writes `ball_trajectory.png`.

### Cappy graph/GNN/HRN
**Files:** `graph/graph_builder.py`, `models/{gat,hrn,hrn_classifier}.py`, `data/`, `visualization/`

`VolleyballGraphBuilder` accepts player/ball/court dictionaries and produces PyG `Data`: 49 features per node, directed player-player and player-ball/ball-player edges, 4 edge features, and node/edge metadata. `GAT` creates node embeddings; `HRN` pools player embeddings by team and forms a global embedding; `HRNClassifier` maps the global embedding to eight activity logits.

`data/ball_player_loader.py` loads ball CSV and player JSON; `training/volleyball_parser.py` parses Volleyball Dataset annotation text; `training/dataset.py` builds graph samples from parsed annotations. `visualization/visualize_graph.py` draws graph/node-feature views. `Cappy_95_GNN_HRN/main.py` demonstrates graph → GAT → HRN embeddings, not video processing or classifier inference.

There are several distinct training implementations: `training/train.py` uses the parser and official dataset splits; `train_dataset.py` parses annotations and uses a court-center ball placeholder; `train_with_real_data.py` uses ball/player logs and frame labels; `train_and_evaluate_real.py` aligns annotation and ball CSV frames and runs classification/relational ablations. Their inputs and assumptions differ.

`ball/main.py` is a separate YOLO ball tracker. It writes an annotated video, per-frame JSON and CSV. `ball/build_real_graph_data.py` reads `merged_graph_input.json`, builds graphs, and writes `real_graphs.pt`; no call from the ball tracker into this builder was confirmed.

### EPV pipeline
**Files:** `epv_phase3/main.py`, `epv_phase3/epv/*.py`, `show_epv.py`

`main.py` processes a video with YOLO player tracking, custom spatial team-ID matching and court homography. It can write player JSON (`--log-out`) and optionally detect/map/log the ball (`--ball-log-out`). It also writes annotated `output.mp4`. It does not call Cappy graph models or the temporal package.

The downstream EPV modules are connected internally: `utils.py` loads/validates logs; `rally_segmentation.py` segments proxy rallies; `state_builder.py` creates 69-D or ball-augmented 76-D states; `action_generator.py` defines six actions and heuristic transition labels; `dataset.py` creates `(state, action, outcome)` samples; `model.py` implements `EPVModel`; `train.py` trains it; `evaluate.py` computes regression/ranking metrics and plots; `show_epv.py` exports action values/recommendations to CSV. `make_ball_log.py` converts pixel ball data through court homographies; `log_report.py` checks player-log quality; `make_synthetic_test_log.py` is a test fixture generator.

The action labels and outcomes are explicitly heuristics/proxies, not confirmed ground truth. Checked-in EPV metadata reports one rally, 69 state features, no ball features, and a homography warning. Metrics also warn that only two unique proxy outcomes exist and should not be interpreted as model quality.

### Temporal package
**Files:** `GritSense_Temporal/src/gritsense/temporal/`

`FeaturePreparer` concatenates supplied feature blocks in stable order; `FeatureStandardizer` optionally standardizes; `TemporalSequenceGenerator` produces chronological windows that do not cross groups; `GRUTemporalModel` and `TransformerTemporalModel` classify windows; `TemporalTrainer` provides training/evaluation. Examples use synthetic data. No repository connection from current video perception or EPV output into this package was confirmed.

### Review 3 snapshot
**Files:** `Review 3/r3/main.py`, `phase3_combined.py`, `phase3_main.py`, `src/inference_onnx_seq_gray_v2.py`, `src/models.py`, local `models/`, `temporal/`, `graph_builder.py`, `sample_data.py`, `visualize_graph.py`, `m3f.py`, `xoxo.py`.

The ONNX inference module processes grayscale frame sequences, decodes heatmap/grid outputs, tracks ball points, estimates radius from motion/contours, and writes CSV plus optional video. `phase3_main.py` reads frame data, builds graphs, runs local GAT/HRN instances, and saves graph/embedding artifacts. `mock_sequence_generation.py` reads saved graph files and builds temporal windows; it does not run temporal classifier inference. `m3f.py` runs player/pose detection; `xoxo.py` overlays ball/keypoint data. This snapshot is not imported by the root or EPV entry points. `main.py`/`phase3_combined.py` refer to `src.pose_detector`, which is absent from `r3/src`.

## 5. End-to-End Data Flow

### Root video script
Video → YOLO player detection/tracking with BoT-SORT → tracked player point mapped using court-corner homography → team-side assignment and speed estimate → annotated frame → `output.mp4`/optional display. No ball tracker, pose model, graph, temporal classifier, or EPV call is present in this flow.

### Cappy ball tracking
Video → YOLO ball candidates → highest confidence for initial point, then nearest candidate to previous center within max distance → trail and per-frame records → annotated video, JSON and CSV. No automatic handoff to GNN code is present.

### Cappy graph/model demo
Player/ball/court dictionaries → 49-D graph nodes and typed directed edges → GAT node embeddings → HRN team/global embeddings. The demo does not run a classifier. Classifier training is implemented in separate scripts with different data preparation paths.

### EPV path
Video → YOLO player tracking → custom spatial team tracker → court homography and speed → optional player log and optional YOLO ball log. Logs → quality report/rally segmentation → 69-D state or 76-D ball-augmented state → heuristic action labels and proxy outcome → EPV MLP training/evaluation → `show_epv.py` CSV of candidate action scores. Rally boundaries, actions and outcomes are not ground truth.

### Temporal path
Feature matrices/blocks → optional standardization → chronological non-crossing windows → GRU or Transformer logits/predictions. Current examples use synthetic data. No current code connects video or EPV output directly into this package.

## 6. Module Relationships

- Root `main.py` uses OpenCV/Ultralytics/NumPy/Torch only; root `BallTracker` is not called by it.
- Cappy `main.py`: sample-data loader → graph builder → GAT/HRN → visualization.
- Cappy training scripts: their separate parsers/loaders → graph datasets/builder → HRNClassifier. Cappy ball tracker is independent; graph builder script is a separate consumer of merged JSON.
- EPV `main.py` writes logs; EPV utility/dataset/state/action modules consume them; train consumes `.npz`; evaluate and `show_epv.py` consume dataset/checkpoint artifacts.
- Temporal components connect internally; no import/handoff from root/Cappy/EPV was confirmed.
- Review 3 `phase3_main.py`: local sample data → local graph builder/GAT/HRN/visualizer → saved embeddings; `mock_sequence_generation.py` reads graph files to make windows. Review 3 ONNX tracking is a separate entry point.

## 7. Important Algorithms/Models

- YOLO detection and BoT-SORT player tracking; custom greedy spatial nearest-neighbor ID assignment in EPV.
- OpenCV homography from four annotated court corners and perspective transforms.
- Ball selection by confidence/distance; Review 3 ONNX supports heatmap/grid outputs, grayscale frame windows, optional GRU state, and motion-mask/contour radius estimation.
- Graph nodes: 49-D features; typed directed player-player and player-ball/ball-player edges; four edge attributes: relative x/y, distance, same-team.
- GAT: edge-aware multi-head `GATConv`, residual projection. HRN: mean pooling within each team, team/global projections, optional ball aggregation. Classifier: eight group activity outputs.
- Temporal GRU uses final hidden state; Transformer encoder mean-pools sequence representations.
- EPV is an MLP over state concatenated with one-hot action. Six actions are scored; action/outcome labels are proxies.
